# Step 22 — Android port (play surface, S-Pen, transports): DONE evidence

Specs: `_work/PHASE4_SPEC.md` §3–§8, `_work/ROADMAP_3.md` Step 22,
`_work/ANDROID_HANDOFF.md`. Decisions: `_work/DECISIONS_3.md` #42–#51 (new),
#1–#41 inherited verbatim — the engine is the same bytes.

**Device:** Samsung Galaxy Tab S8 Ultra (SM-X906B), Android 16 (API 36),
Adreno 730, GLES 3.2, 2960×1848 @ 120 Hz (EGL surface capped to 1480×924 per
DECISIONS_2 #31; sim_scale 0.75 → 1110×693 field). S-Pen = the `sec_e-pen`
Wacom EMR digitizer (pressure 0..4095, ABS_TILT_X/Y, ABS_DISTANCE — the app
reads it as `getPressure` / `AXIS_TILT` / `AXIS_ORIENTATION` and
`ACTION_HOVER_MOVE`).
**Host:** the Linux box (Ubuntu 25.10), which is both the build machine and
the DAW end of every transport — the tablet's USB-MIDI gadget and its BLE-MIDI
peripheral both land on this machine's ALSA sequencer.

**Build:** Gradle 8.14 / AGP 8.10 / Kotlin 2.1.20 / NDK r27c, arm64-v8a,
`externalNativeBuild` → repo-root CMake. `libsumi-shell.so` now links
`libhostmpe.a` (the shared host library, consumed through JNI exactly as
Swift consumes it through the module map) and carries the two headless
suites with `main` renamed, so they run on-device.

## What landed

**Native (`android/cpp/`)** — split into `sumi_jni.cpp` (surface/EGL render
thread, AMidi ingest, evidence hooks; unchanged in substance) and
`sumi_play.cpp` (the Phase-4 host: `hostmpe_t`, the strip engine, one limiter
per transport, the byte log, the storm, the on-device suites), with `shell.h`
between them. All hostmpe state and every generated byte live on the **AMidi
poller thread** — the §5.2 single producer (DECISIONS_2 #33 / #46): the UI
thread posts commands, touch-down/pen-down are microsecond sync hops for the
voice id, and outbound wire writes are a JNI upcall to Kotlin, which owns the
endpoints. Host-owned params moved into a shell snapshot so the instance-free
probe answers on the UI thread with no queue round trip (#47).

**Kotlin** — `PlayOverlayView` (probe-swept two-tone lattice, per-touch
joystick indicators, fingers, S-Pen, hover ghost, saturation blink),
`ControlStripView` (floating top-left palette: Pitch spring, Mod latch, two
assignable wheels with a long-press CC editor, momentary Sustain),
`MidiOutputs` (USB gadget port + status, virtual device, BLE),
`SumiMidiDeviceService` (the virtual MIDI device), `BleMidiPeripheral` (a
GATT server — Android's MidiManager is central-only, #44), settings parity
with the iOS sheet, and the Marble-mode two-finger pinch (#41).

**Bugs caught by the evidence, and by an independent review of the diff**
(#44, #54 — the review's full batch is in DECISIONS_3 #54). The evidence
caught this one: the BLE framer
built one packet per `send()` and capped the backlog by dropping the OLDEST
packet, so the 80-message MCM/RPN0 burst queued ~79 single-message packets and
the cap ate the master MCM plus the first four members. The Linux capture
showed it as "RPN 0 = 48 on 11/15 members" with no MCM. Messages now coalesce
into the tail packet and the cap drops from the newest end; the same capture
then reads 15/15 with the MCM in order.

The review caught, among others: `nativeSurfaceDestroyed` could block the UI
thread forever (the §5.4 contract inverted, latent since step 14) when a
destroy arrived while the render thread was parked with no surface; a lost
wakeup in the render-thread command queue; an `AMidiDevice` double-free for
any multi-output-port device, and removed devices never leaving the poller;
`MidiInputs` never unregistering its `DeviceCallback`, which after a relaunch
in the same process ingested every message twice; BLE flow control stalling
permanently when one of several centrals dropped mid-notification; and the
safety valve discarding §5.3's never-dropped class from the tail. **And two
false greens in this evidence tooling** — the sustain assert was a no-op
(`stuck = (v == 127)` assigns rather than accumulates) and `capture` mode
passed on an empty file. Both fixed, both now negative-tested; every assert
artifact here was regenerated with the corrected analyzers, and the pen
analyzer ships with a negative control
(`pen_trace_negative_control.csv`: the same stroke with its crossing bend
replaced by center fails at 3.81× the bound, where the real traces sit at
0.43–0.46×).

## Late additions after the step's first pass

Two changes landed after the DONE table above was measured, both at the user's
direction; the table's asserts were re-run and still hold.

* **DECISIONS_3 #57 — the piano grid's accidental knob, one line in the CORE**
  (`layouts.cpp`), resolving the #56 flagged question. The hit region was
  always right; the drawn/travel radius lost the 0.6 proportion above aspect
  1.5873, so the same build read correct on an iPad and un-narrowed on this
  16:10 tablet. The accidental footprint is now scaled in both axes, the
  golden pins the ratio at seven aspects (four past the old crossover, with a
  negative control), and the pen glissando is still natural-only on device.
  Evidence: `piano_accidental_knob_fix.txt`, `piano_grid_accidental_knobs.png`.
* **DECISIONS_3 #58 — the S-Pen barrel button is a sustain pedal**, driving
  the same `hostmpe_strip_t` engine as the §8 palette's pad. Evidence:
  `pen_button_sustain.txt`, `pen_button_sustain_byte_log.csv`.
* **DECISIONS_3 #61 — the glissando corridor (the user's design).** A natural
  shrinks to the accidental's size and sits flush with its old bottom, so the
  strip above it belongs to the black keys alone. A corridor sweep now plays
  the pentatonic C#4 D#4 F#4 G#4 A#4 with zero naturals, where the same

  Evidence: `piano_glissando_corridor.txt`, `piano_glissando_corridor.png`,
  `piano_glissando_byte_log.csv`.
* **DECISIONS_3 #60 — a pre-existing piano-grid bug the user spotted, fixed.**

  One line: the natural is centred on its octave PAIR, which is what its
  radius has described since #29. The invariant is now pinned by a golden
  that scans the probe and compares it with the drawn cell. Evidence:
  `piano_cell_alignment.txt`, `piano_cell_alignment.png`.
* **DECISIONS_3 #59 — ROLLED BACK, nothing shipped.** A black-key glissando

## What still needs you (hardware / human in the loop)

Everything above is measured and green on the device. What is left is what a
script cannot do.

**A note on how the last checks were run:** toggling the USB gadget function
drops adb when adb rides that same cable, so the device-removal and
relaunch checks were run over **adb on Wi-Fi** (`adb tcpip 5555`, connect to
the tablet's LAN address). Worth remembering for any future USB-mode work.
adb has since been restored to USB-only (`adb usb`).

1. **One S-Pen barrel-button click** (DECISIONS_3 #58, added after the step's
   first pass). The wiring is verified on device through a simulated click —
   CC 64 = 127/0 on the master channel, byte-log asserts green — but
   `sendevent` on the pen's input node is denied to the shell user, so the OEM
   event-delivery path needs a human. The app is running in Play mode on the
   chromatic grid right now; click the pen's button once near or on the glass
   and read:
   `adb logcat -d -s sumi-shell | grep "barrel button"`
   Two lines (pressed / released) means the whole path works. Nothing means
   Samsung's Air command swallowed the click — turn it off under Settings →
   Advanced features → S Pen → Air actions, and try again with the tip down.

2. **Channel-steal confirmation with the ROLI over BLE** (§5.1 masking). The
   mechanism is now verified on device against a live external MPE chord
   (`channel_steal_masking.txt`), so what remains is the DONE gate's literal
   wording: the same test with the ROLI, over BLE. Power it, pair it from the
   settings dialog's Bluetooth entry, hold a chord across ≥ 4 member channels
   while six touches play, then
   `adb shell am start -n com.vibetuned.midisink/.MainActivity --es flushLogs 1`
   and run `python3 tools/midi_asserts.py device midi_log.csv` — the line to
   read is "zero touch allocations on externally-held channels".
3. **An on-device Android DAW.** The virtual device is published and a client
   opening it re-sends the handshake, but the tablet has no DAW or MIDI
   monitor installed, so nothing has received it yet. Install any app that
   lists MIDI inputs (a MIDI monitor is enough) and confirm "midi-sink Play
   Surface" appears with the MCM/RPN 0 = 48 handshake on connect.
4. **S-Pen velocity calibration** (#43). `adb shell input stylus` synthesizes
   pressure 1.0, which only proves the top of the curve (velocity 127, as
   logged). The two constants `PEN_P_BASE` / `PEN_P_HARD` in
   `PlayOverlayView.kt` set where "a baseline tap = 96" and "hard = 127"
   land; a few real taps will tell you whether 0.15/0.75 is right on your
   hand.
5. **The subjective pass** — the 10-minute session was scripted (`adb shell
   input` taps, swipes and stylus strokes over the storm). Whether the
   surface FEELS like the iPad does is yours to say, and it is the one gate
   no script can assert.
