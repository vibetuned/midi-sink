## Step 29 — deliverables

1. **Verify + polish** the shared settings window and `--dev` on Windows
   (this step owns any Windows-only fixes; the core stays frozen — Step 33
   is the scoped unfreeze). Things to actually exercise: the second GLFW
   window's GL 3.2 context beside the D3D11 main window, `Ctrl ,` reopening

   folder, the INI round-trip, and that a release build refuses every debug
   key without `--dev`.
2. **`windows` job in `release.yml`**, per the LANE INTERFACE: `needs:
   [version, gates]`, MSVC + Ninja (the `gates` job shows the toolchain
   steps: `ilammy/msvc-dev-cmd`, `choco install ninja`), build with the
   injected version, artifact **`dist-windows`** containing
   `midi-sink-<version>-windows-x64-setup.exe` (installer) and
   `midi-sink-<version>-windows-x64-portable.zip`; uploads guarded by
   `dry_run`. Installer technology is your call (Inno Setup and NSIS are both
   on the runners; the siblings' Tauri builds use NSIS) — record it. The
   installer must register the Start-menu entry, the icon, and an
   uninstaller; settings in `%APPDATA%` are the user's and survive uninstall
   unless they opt in.
3. **Signing-if-cert-present.** If the author provides a certificate secret,
   `signtool` the exe and the installer with a timestamp; if not, ship
   unsigned and **document the SmartScreen consequence in the README** ("More
   info → Run anyway", once per new version) rather than fight it. Record the
   decision either way.
4. **winget bump on `release: published`**: copy the sibling
   `publish-winget.yml` (`../battuta/.github/workflows/publish-winget.yml`):
   detect the manifest under `manifests/v/Vibetuned/MidiSink`, find the
   `*-setup.exe` asset, `wingetcreate update Vibetuned.MidiSink --version
   --urls --submit`. **The first version is submitted by hand** (moderation
   wants a human on the initial PR): `wingetcreate new <setup.exe URL>` with
   identifier `Vibetuned.MidiSink`, publisher `Vibetuned`, license
   `AGPL-3.0-only`, URLs above — stage the resulting manifest under
   `packaging/windows/winget/` so the conventions are in the tree. Until it
   is merged the workflow detects the missing manifest and skips, as the
   siblings do. Note for RC tags: winget-pkgs does not want pre-release
   versions — the workflow should skip when
   `github.event.release.prerelease` is true (the cask flow opens a PR
   instead; here there is no safe equivalent), record it.
5. README (Windows install paragraph: installer, portable zip, `winget
   install Vibetuned.MidiSink`, SmartScreen note) and the site's
   `site/src/content/docs/guide/install.md` Windows paragraph.

## Gotchas known from the macOS lane

* The `publish` job's `needs` list gates the draft: a missing or red
  `windows` job blocks every platform's draft — run the workflow with
  `dry_run` first (Actions → release → Run workflow) before asking the
  author for a tag.
* Asset naming is the interface; `publish-winget.yml`'s `-setup\.exe$`
  match depends on it.
* Everything you can prove without a certificate or a runner (the installer
  builds, installs on a clean VM, uninstalls, About reads the version) goes
  in `docs/evidence/step29/SUMMARY.md` with the raw outputs beside it; what
  needs the runner or the author is listed as YOURS with the exact steps.
